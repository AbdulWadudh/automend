# Deploying Automend on Coolify

Everything except SigNoz deploys as **one Coolify resource** from
[`docker-compose.yml`](docker-compose.yml) in this folder: Postgres, Redis (Dragonfly), the
migration runner, the API, the worker and the web app.

> This is **not** the repo-root `docker-compose.yml`. That one is local development only — it
> publishes ports on the host and runs throwaway credentials. This one keeps everything on a
> private network and exposes exactly one thing: the web app.

## Why one stack

| | One stack (this) | Separate resources |
|---|---|---|
| Postgres / Redis reachable from the internet | No — private network | Yes, unless you disable it |
| Dragonfly's BullMQ flags | In `command:`, cannot be lost | `DFLY_*` env vars you must remember |
| Service addressing | `postgres`, `redis`, `api` | UUID-suffixed container names |
| Deploys | One | Six |

The Dragonfly point is the important one. BullMQ's Lua scripts access keys they do not declare;
Dragonfly refuses that by default. **Every health check stays green while job processing fails
completely** — `/health` reports Redis "up" because `PING` works. In this stack the flags live in
`command:` where they cannot drift.

## Deploy

1. **New Resource → Docker Compose**, source = this repo, compose path
   `deploy/coolify/docker-compose.yml`.
2. Set the one required variable:

   ```
   OTEL_EXPORTER_OTLP_ENDPOINT=https://<your-signoz-collector-domain>
   ```

   Base URL only — no `/v1/logs`, no port. Deployment fails fast with a message if it is unset,
   rather than starting a stack that silently ships no logs.

3. Assign a domain to the **web** service (container port `8080`). Coolify fills
   `SERVICE_FQDN_WEB_8080`, which also becomes the API's `WEB_ORIGIN`.
4. Deploy. Postgres and Redis credentials are generated by Coolify
   (`SERVICE_USER_POSTGRES`, `SERVICE_PASSWORD_POSTGRES`, `SERVICE_PASSWORD_REDIS`) and are
   visible and editable in the UI. The session signing key (`SERVICE_PASSWORD_64_AUTH`) is
   generated the same way — **rotating it signs every user out**, so leave it alone unless you mean
   to.

Nothing else needs configuring. Migrations run automatically: the `migrate` service applies them
before the API and worker start, on every deploy.

### Signing in with Google

Optional — email and password work without it. To enable it, create an OAuth client in the Google
Cloud console, register this exact redirect URI:

```
https://<your-web-domain>/api/v1/auth/callback/google
```

and set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Both are needed: with only one set the
button stays hidden rather than failing at the redirect. Note the URI points at the **web** domain,
not the API — the browser only ever talks to the web app, which proxies onward.

### Optional variables

| Variable | Default | Notes |
|---|---|---|
| `LOG_LEVEL` | `info` | `fatal`…`trace` |
| `POSTGRES_DB` | `automend` | |
| `WORKER_CONCURRENCY` | `5` | |
| `GOOGLE_CLIENT_ID` | empty | Set with the secret to offer Google sign-in |
| `GOOGLE_CLIENT_SECRET` | empty | |
| `OTEL_LOGS_ENABLED` | `true` | `false` for stdout logging only |
| `OTEL_EXPORTER_OTLP_HEADERS` | empty | Ingestion key for a hosted backend |

## SigNoz

Separate resource, separate lifecycle — see [../signoz/README.md](../signoz/README.md). This stack
only ever needs its collector URL.

If SigNoz runs on the same Coolify instance, enable **Connect To Predefined Network** on both and
point `OTEL_EXPORTER_OTLP_ENDPOINT` at the collector's internal name, so telemetry never leaves the
host and the collector needs no public domain. Note that cross-stack service names carry a UUID
suffix (`otel-collector-<uuid>`), unlike the plain names used inside this stack.

## Verifying a deployment

From the **worker** service's Terminal:

```bash
bun run preflight
```

Checks Postgres, Redis, **BullMQ's Lua scripts** and the OTLP collector, and exits non-zero on any
failure. The BullMQ check is the one that matters — nothing else catches a Dragonfly missing its
hashtag-locking flags.

Health endpoints, if you want them from outside: `api` and `worker` expose `/health` on 3000 and
3002 and answer `503` when Postgres or Redis is unreachable. They have no domain by design; reach
them from the Terminal or give them one temporarily while debugging.

## What is exposed

Only the web app. The API, the worker, Postgres and Redis have no domain and no published ports —
they are reachable only from inside the stack. The browser talks to the web app, which proxies
`/api` to the API and `/otlp` to the collector from within the network.

A self-hosted SigNoz collector has **no authentication**, so if you give it a public domain anyone
who finds it can inject log records. Prefer the internal-network route above.
