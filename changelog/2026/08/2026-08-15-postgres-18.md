# Move the local stack to Postgres 18 and fix its volume mount

- **Date:** 2026-08-15
- **Type:** chore
- **Scope:** `packages/shared`, `docker-compose.yml`

## Summary

The local Docker Compose stack now runs `postgres:18-alpine`, matching the deployed database, and
mounts its data volume at the path Postgres 18 actually uses. Container image tags moved into
`config.ts` alongside every other configured value.

## Why

The deployed Postgres is 18; local development was on 17. Developing against a different major is
how a migration passes locally and fails in production.

Bumping the tag alone would have been worse than leaving it. **Postgres 18 changed where the data
lives**, and the change is silent:

| | `PGDATA` | declared `VOLUME` |
|---|---|---|
| `postgres:17-alpine` | `/var/lib/postgresql/data` | `/var/lib/postgresql/data` |
| `postgres:18-alpine` | `/var/lib/postgresql/18/docker` | `/var/lib/postgresql` |

Mounting the old `/var/lib/postgresql/data` against an 18 image gives a container whose database is
written *outside* the mounted volume. Everything works — queries, migrations, health checks —
until the container is recreated, at which point the data is gone. Nothing warns you.

## What changed

- `docker-compose.yml` uses `${POSTGRES_IMAGE}` and `${REDIS_IMAGE}` rather than literal tags, and
  mounts the data volume at `${POSTGRES_DATA_PATH}`.
- `config.ts` gains `localDev.postgres.image`, `localDev.postgres.dataPath` and
  `localDev.redis.image`, so the image versions are declared once and flow into `.env.example`
  like everything else.

## Action required

**The local Postgres volume must be recreated** — data written under the old path is not readable
by an 18 image at the new one. Local data is disposable and migrations re-run on `up`:

```bash
docker compose down -v
cp .env.example .env      # regenerated: adds POSTGRES_IMAGE, POSTGRES_DATA_PATH, REDIS_IMAGE
docker compose up -d --build
```

Deployed environments are unaffected — Coolify manages its own Postgres volume.

## Verification

- `postgres:18-alpine` and `17-alpine` image metadata inspected directly to confirm the `PGDATA`
  and `VOLUME` change, rather than taken from documentation.
- Running container reports `PostgreSQL 18.6` with `data_directory = /var/lib/postgresql/18/docker`.
- **Persistence proven, not assumed:** wrote a marker row, ran `docker compose down` and back up,
  and read the row back — the case that silently fails with the old mount path.
- Migrations applied on 18 and the `flows` table plus its tenant index are present.
- Full stack healthy; api, worker and web `/health` all 200.
